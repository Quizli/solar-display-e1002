# Insights v2 — implementation contract

Status: curated implementation brief. The five sibling JSON files are the editorial source of truth, not live code. Use their exact templates and numeric assumptions. Do not generate new copy or invent values to fill a missing context. Changes to wording should be limited to necessary corrections for grammar/width and documented explicitly. The frozen 800×480 SVG and existing responsive web layout remain unchanged.

## 1. Outcome and scope

Replace the existing 32 hard-coded energy facts, tiny morning pool and 3 historical types with a shared, deterministic, data-driven system. The five content worlds are energy, morning/status, history, calendar/season, milestone. There is deliberately no standalone system-fact category. The resident-facing tone is clear Swiss High German, dry intelligent humour, surprising but understandable; no ß. All equivalent consumption figures are illustrative assumptions and not guarantees or measurements.

Inputs: `energy-catalog.json` (76 concepts, two variants each), `morning.json` (14 types), `history.json` (17 types), `calendar.json` (26 rules), `milestones.json` (8 types). These are machine-readable templates plus human-readable eligibility specifications. English condition descriptions are documentation, NOT executable expressions; implement explicit typed handlers. Keep IDs stable. Retain assumptions and source URLs in source control, never expose internal configuration/counter baselines in public payload.

Do not change collector polling, Fronius adapters, raw measurements, aggregate math, stale-total-counter baseline fix, daily yield calculations, existing qualification of complete days, self-consumption, CO2, battery/grid direction, chart thresholds or scales. SVG chart stays fixed 24 kW; leave current web scaling alone. Internal grid <0 is import; >0 export. Grid chart threshold 0.5 kW remains unchanged. Existing data and fact history must survive deploy/rollback. Any schema change is additive, idempotent, tested on a populated copy. Do not reset or delete existing data.

## 2. Implementation phases (one draft PR, two reviewable stages)

Start from the branch containing these documents, or create a new branch from it. First implement loader, calculation registry, formatting/wrapping, compatible selection persistence and contract tests. Then implement the dynamic stories, milestone/calendar state and simulation, replace legacy selection and integrate both outputs. Keep stages as distinct commits. This avoids a half-finished deployment and still isolates technical from editorial changes. If cloud Codex cannot work directly on the planning branch, include these documents verbatim on its new branch based on current main. Open a draft PR against main, or update the existing planning draft. Do not merge or deploy automatically.

JSON is selected instead of YAML: current project uses the standard library, and the Dockerfile copies the whole repository. Place the active source files in dashboard/facts/content/ (move, do not maintain duplicate divergent copies); update the document links accordingly. Load once and validate upfront, with explicit allowed IDs, groups, branches, typed finite positive factors, supported variables, valid thresholds, unique aliases and templates. Reject unknown placeholders and invalid entries in CI; no eval, dynamic code in content, LLM/API at runtime, or extra network requests per fact. Standard library preferred. Use a small schema/version and generic typed calculation/rendering registry. Do not replace measurement storage.

## 3. Energy catalogue

Implement runtime, uses, distance, quantity:
- runtime: hours = energy_kwh * 1000 / power_w. Render {duration} INCLUDING unit. Adaptive approximate seconds, milliseconds if below 0.1 s, minutes, hours, days, years. Use human-friendly rounding, choose units to avoid "0 Sekunden" or implausible huge hour counts; singular/plural correct. Do not imply elapsed actual appliance use. Include source assumptions for Gösgen (1,010 MW nominal net; conditional, not live) and CERN (600 GWh/year annual average incl. LHC experiments and general services); verified primary URLs in catalogue.
- uses: count = energy_kwh / kwh_per_unit. Conceptual approximate full uses, rounded sensibly, suppress if rounded count <1. No false precision.
- distance: km = energy_kwh / kwh_per_km, sensible rounding, suppress rounded zero. Inputs explicitly illustrative (not actual VBZ data).
- quantity: value = energy_kwh / kwh_per_unit, decimal allowed, adapt precision/units only as consistent with the provided literal template; never round to misleading zero.
- {when} is exactly heute or gestern; {energy} is the same actual yield displayed, with Swiss decimal comma / apostrophe grouping and at least two decimals for <1 kWh if needed. No blank reference to "damit" with no antecedent. All other variables formatted, no raw Python repr.
- min_kwh inclusive, max_kwh null = unbounded; valid positive finite energy only. Energy eligibility uses existing first completed 5-minute hourly anchor (or a fresh valid first current-day anchor on startup), display values may update while selected ID/template is stable. Never freeze the numeric output. Maintain previous-hour bridging briefly while next anchor arrives. If current rendered variant cannot fit, try other variant for same ID; do not silently emit overflowing text.
- Active and after-sunset energy stories refer to today's measured yield only. Before first meaningful production, morning pool normally wins; yesterday equivalents may be rare fallback if yesterday is qualified and period explicitly yesterday. Do not consume the active-production hourly slot or re-label an existing yesterday selection when the phase changes.
- Keep all 27 retained legacy IDs as lookup aliases to new canonical IDs; 5 retired IDs are ignored for new choices. Legacy historic rows remain; count mapped aliases towards repetition avoidance. On cutover, resolve a retired or unrenderable stored ID to a safe new candidate without destructive rewriting of historical rows.

## 4. Text layout and rendering

Single semantic sentence/string per variant. Shared width helper measures existing conservative Arial-compatible widths; no content-authored newlines. Try entire text on one line (<=490 px); if fits, line_2 = "". Otherwise choose whitespace split to keep both lines within 490 px, favour punctuation/clause boundaries and balanced widths (penalize a very short orphan), preserve words/numbers and punctuation. Keep number + unit together where possible. If normal fails, try another approved variant, then use existing 510 px hard limit. Reject a candidate if no variant fits. Prefer sensible wrapping over forced two-lines. Never truncate or split inside a word. Test actual SVG geometry at both limits, including glyphs and large counts.

Web insight must display natural paragraph wrapping independently of SVG line splits. Inspect HTML/CSS/JS: current dashboard.js uses payload.insight.line_2 || DASH; change to suppress empty line instead of rendering a dash. Join only nonempty parts with a single space; if both missing, existing placeholder. Preserve existing font/spacing/layout. SVG retains STORY_LINE_1 and STORY_LINE_2 placeholders (second may be empty) and correct escaping. No line changes to other sections.

## 5. Shared input and data quality

Reuse build_fact_context, build_live_view and existing history candidates. Compute completed_record_daily_yields(today) once per publishing evaluation (existing single bulk query, no query per day/candidate). Share the returned immutable qualified list, its date map and derived statistics between morning, milestones, history and public payload. Do not re-query in web_publisher._historical or reconstruct independent facts. Build one renderer-independent selection per evaluation; SVG and JSON receive same insight ID, variant and content. SVG refresh remains five minutes, JSON 15 seconds (normal transient lag acceptable).
- Qualification of past days remains exactly as existing SolarDatabase.completed_record_daily_yields/_qualify_record_day (real UTC day length including DST, 95% unique 5-minute coverage, first/last and maximum 10-minute gaps). No fallback from qualified list to incomplete daily_yield_from_aggregates for claims about yesterday, rank, counts, records or series. Valid zero-yield days qualify; missing is not zero.
- Do not change daily-energy calculation. Context must distinguish today's actual local day from timestamp of latest power measurement at midnight, and freshness. Do not use yesterday's value as today in first minutes after midnight. No record/threshold claim or milestone state writes on missing/stale snapshots. Existing stale/missing status overrides all content. Do not set history or calendar dates from an old snapshot.
- For a new running-day production record or barrier, require fresh same-local-date snapshot, reliable nonnegative finite current-day cumulative yield (DailyEnergy.complete and valid source; never use a partial/stale baseline or incomplete integration), qualified-to-cutoff completed buckets (same unique coverage/gap rules applied from local midnight to last completed bucket; no future buckets) and a plausible nondecreasing cumulative reading. At least two earlier qualified days for record and first barrier; don't fabricate missing days. Existing 0.1 kWh record margin. If quality cannot be established, no claim. Past qualifying rules unchanged.
- All date/time keys use Europe/Zurich and actual UTC instants for elapsed durations/order, include DST fold. On simulation, filter all raw/aggregate/history/forecast data strictly as-of each simulated instant; never use future data.
- SunData currently provides sunrise, sunset, daily weather_code, predicted sunshine_hours. Propagate sunshine_hours and freshness into FactContext. Forecast only when valid for requested local date and within configured max cache age. Daily WMO code is a forecast, not observed morning conditions. Do not promise actual production or quantify predicted kWh. No inferred weather cause of zero production.
- DAYLIGHT_CHANGE needs yesterday's solar times: preserve yesterday's successfully fetched daily astronomical values in backward-compatible atomic cache (or calculate locally using verified coordinates and a tested astronomical method). Never treat forecast sunshine as daylight. If yesterday unknown, omit this candidate; no request per render. Cache old format still works.
- Seasonal astronomical event dates must be exact Zurich local dates from a documented astronomy algorithm/library or versioned verified date table for supported years, with tests around solstices/equinoxes and year boundaries. Skip if unsupported. Do not hardcode 21st of a month as astronomy. Calendar Easter dates via tested Gregorian computus and TZ transitions. Nine legal Zürich holidays are documented by official source; other special days are explicitly cultural/seasonal.

## 6. Selection and persistence

One consistent selector, two independent slots: shared insight and web historical_comparison. No separate standalone system facts. Existing hourly stable ID and numeric anchors preserved where applicable. Candidate includes canonical ID, family, semantic key (concept + reference date/window), context, template branch, stable variant index/key, priority, eligible phase and expiry. Never use unseeded random or changing numeric value in choice seed. Use stable hash of local slot, candidate ID and stable event/reference identity. Persist selection with variant index/key in SQLite context_json or new versioned selection table. Read-only mode must make no writes. Avoid scanning all past selections each 15 seconds; bounded indexed lookup, preserve DST ordering. Old rows remain readable.

Priority:
1) data missing/stale safety;
2) active milestone(s) for today;
3) calendar special (once in morning, at most one other daytime slot; if no morning opportunity, use one daytime slot; never all-day);
4) record-afterglow one morning slot, not full next day;
5) morning/status before meaningful current-day production;
6) active/after-sunset energy rotation (history already has own tile; SVG may display a non-redundant history insight at most once per day).
On conflict between calendar and record afterglow, ensure both have a chance at distinct morning slots; afterglow wins first if both unshown. Calendar lead-up/season start is an ordinary morning candidate, not override. A milestone overrides immediately even midhour. Normal phase transition from morning to active at >=0.1 kWh or fresh PV >=0.1 kW; only valid nonzero energy enables an equivalent. Late waiting threshold 90 minutes; if missing sunrise use conservative existing clock fallback without claiming exact astronomy. After sunset with fresh yield <0.1 kWh use ZERO_DAY_COMPLETE. Positive yield remains today's energy after sunset. Missing solar measurements not a zero day.

Ordinary selections stable hourly, re-evaluate when phase changes or selected candidate becomes invalid. If phase transition within same hour needs a new selection, key must distinguish phase/slot (or use a compatible additive table); do not let INSERT OR IGNORE of old hour trap new phase. Preserve prior real selection in audit/history. Ordinary energy: staged avoidance of same day, last 24/12/6 actually selected canonical IDs, previous family, then least recently used valid alternative. Strongly avoid adjacent repetition when alternatives exist; never return no story merely due to cooldown. No all-history scans. Morning: meaningful history/weather/daylight first, weighted deterministic ordering (priority bands, not simply max), rotate semantic categories, avoid previous morning concept if alternatives and yesterday's same concept where feasible; low-priority contextual status only when few useful candidates; afterglow exactly one slot. Do not persist an unavailable anchor fallback as a permanent energy choice. Persist text variant/branch for stable slot, forecast changes may update numbers if still same valid branch; if eligibility changes, replace deliberately rather than showing a false assertion.

## 7. Milestones

Detailed trigger/threshold/template data in milestones.json. Require explicit optional environment config SOLAR_COMMISSIONED_DATE (ISO local date), SOLAR_COMMISSIONING_TOTAL_KWH (nonnegative finite original Fronius total at commissioning). Add to .env.example and compose publisher env, never hardcode unknown real values, never infer commissioned date from July monitoring start. Missing config disables only dependent age/anniversary/lifetime milestones. Others use observed qualified history. No retroactive celebration on first installation of v2: initialize a persistent watermark from current valid counter and pre-existing qualified history; already-passed thresholds acknowledged silently, not all today. Date anniversary occurring on first enabled day can display if date configured. If initial valid counter unavailable, initialize on first valid observation without celebrating old thresholds.

New additive idempotent event state (table e.g. milestone_events plus counter watermark/state) with unique stable event key, trigger local date/time, activation date, expiry, frozen factual context/template key, detected/acknowledged state. An event persists across restarts, concurrent publishing and refreshes; record value can update if valid fresh yield rises, never change prior record baseline mid-event. Do not mark a newly triggered event as consumed and suppress the same day. It is active until local midnight, not UTC midnight. Once-only crossings permanently deduplicated. Record IDs unique per local day; anniversary by year; streak threshold per distinct run and length; new streak record per run/length. Age is elapsed calendar days, day zero at commissioning; use exact singular first anniversary and leap-day rule. A completed-day count/streak is recognized from yesterday only, on following local calendar day; never resurrect old events after outage.

Lifetime: counter minus confirmed baseline, not sum of incomplete daily yields. Persist last trusted counter, timestamp and highest acknowledged threshold. Require two consecutive fresh valid observations spanning crossing with same local day and continuous monotonic counter; if gap crosses midnight or long outage prevents dating the crossing, acknowledge silently. Reject NaN, negative, reset/downward jumps; do not rebase automatically or celebrate twice; disable lifetime events until verified continuity/config correction. Bound implausible positive jumps using configured physical upper bound (24 kW * elapsed hours plus documented meter tolerance); if impossible, suppress/quarantine and log. During initialization multiple old thresholds are acknowledged; during a real interval crossing multiple due thresholds, keep highest meaningful event and acknowledge lower ones, avoiding repetitive headlines.

All-day ownership of insight: calendar age/anniversary + completed-day events from midnight; running events immediately after verified crossing through midnight. If multiple events active, sort priority descending then stable key; rotate only those events hourly, show a newly triggered highest-priority event immediately, keep each template stable. No normal insights mixed into active milestone day. Deduplicate overlapping semantics: STREAK_RECORD supersedes HIGH_YIELD_STREAK of same run/length; PRODUCTION_BARRIER highest reached only; a barrier and daily record are distinct claims but may be combined only using approved texts (otherwise rotate). Keep history tile independent and suppress semantically redundant statements, not merely identical text. Record afterglow only next morning, not pinned next day. No battery/meter-count/monitoring uptime milestones.

## 8. Historical tile

Use explicit eligible handlers for the 17 types in history.json, sharing precomputed history stats. All sums/mean denominators exactly as specified. Label actual dates with Swiss month names, include year when outside current year. Never "Am Vergleichstag". Distinguish "letzte 7 vollständige Tage" from calendar week; require all calendar days for calendar week/month or streak. Ranks descending, ties at displayed precision suppress rather than claim unique rank. For percent differences, use abs values in prose with correct higher/lower, positive baseline >=0.1 kWh; null percentage for zero baseline, absolute variants if specified. Use similar only within stated threshold. For zero days never invent denominator. Streak ends only when actual yesterday qualified and below threshold, not missing.

Rotate history independently (suggest 3-hour stable local slot, different concept from last tile where possible, same slot stable across refresh/restart). No hardcoded HIST_AVERAGE preference. Avoid same semantic key/type and reference window as current insight, including YESTERDAY_RANK vs HIST_RECENT_RANK, RECORD_AFTERGLOW/DAILY_RECORD vs record age, STREAK_RECAP vs streak. Prefer alternate meaningful history rather than duplicate; if none, null. For older latest qualified date use date, not yesterday. Avoid repetitive data from ancient gaps by explicit date references and expiry for yesterday claims; all-time record age remains useful.

Inspect public JSON schema and web JS validator: today direction only allows higher/lower/similar, but totals/rank/date facts have no comparison. Extend contract with honest direction "neutral" for noncomparative types, null comparison/baseline/pct values as appropriate. Keep existing nullable fields and type/statement/reference_day/comparison_day/baseline_days. Update JS validation, neutral icon styling using existing neutral visual language, README/schema fixtures/tests. Do not assign fake direction or numbers. Keep existing schema version 1.0 with additive compatible enum support within coordinated deploy, or document bump if necessary and ensure UI tolerates both old and new payload during rollout. Web history shows statement as a natural paragraph. SVG has only insight slot; history should not change layout.
